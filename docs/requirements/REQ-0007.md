# REQ-0007: Базовый переносимый маршрут навыка

## Определения

**Базовый маршрут P0** — полезный основной результат навыка, который агент
может получить по инструкциям и возможностям целевой задачи без запуска
поставляемого скрипта, установки интерпретатора, загрузки пакета или наличия
POSIX-оболочки.

**Автоматизированный маршрут P1** — необязательное ускорение или проверка,
которым нужен явно объявленный переносимый интерпретатор или исполняемый файл.

**Платформенный маршрут P2** — необязательное действие, привязанное к явно
названной операционной системе, оболочке или оснастке.

## Требование

Каждый навык общего назначения должен иметь базовый маршрут P0. Отсутствие
Python, Node.js, POSIX-оболочки, сети или возможности установить пакет не должно
лишать пользователя всего полезного результата навыка.

Навык без P0 допустим только тогда, когда его предмет по своей природе зависит
от конкретной платформы или исполняемой среды. Такое ограничение должно быть
явно указано в поле `compatibility` и в процедуре навыка. Навык нельзя объявлять
переносимым за пределами этой среды.

## Критерии приёмки

1. У навыка со скриптами описан P0 либо обосновано обязательное ограничение
   среды.
2. P0 не требует запуска файла из `scripts/**`, установки пакета или доступа к
   сети.
3. Инструкция различает P0, P1 и P2 и не выдаёт платформенный маршрут за общий.
4. Проверка коллекции отклоняет новый навык со скриптами без объявления
   совместимости и базового маршрута.
5. Сценарий результата проверяет случай, когда Python и POSIX-оболочка
   недоступны.
6. Каждый публичный Python-скрипт P1 первого уровня в `scripts/` имеет
   исполнимый контракт с реалистичной фикстурой и хотя бы одним успешным
   рабочим сценарием. Ожидаемый отказ не заменяет успешный сценарий. Контракт
   запускает поставляемую команду и проверяет внешний результат. Команды из
   процедуры навыка сопоставлены со сценариями контракта. Для сохранённого JSON
   рабочий сценарий выполняет запись и повторно читает созданный файл.
   Учёт входных данных и ожидаемого отсутствия путей соответствует REQ-0007.1
   и его критериям приёмки ниже.
7. Контроль качества публикуемой коллекции до и после остальных проверок
   отклоняет `__pycache__`, `.pyc` и `.pyo` в `.apm`, `.agents`, `.claude`,
   `.codex`, поставляемой оснастке и семантических путях `apm.lock.yaml`.
8. Для обычного Python-процесса процедура применяет наследуемую переменную
   `PYTHONDONTWRITEBYTECODE=1` либо ключ `-B` для одного подтверждённого
   процесса. Явные `py_compile` и `compileall` запрещены над защищёнными
   деревьями, потому что обе профилактические меры не останавливают компилятор.
9. Синтаксическая проверка Python читает исходник и компилирует его в памяти
   без импорта и записи байткода либо использует эквивалентный валидатор.
10. Самоприменение APM выполняет барьер до установки, после установки и после
    аудита. Если загрязнён файл блокировки, его пересоздают штатной установкой
    из чистого исходного дерева. Ручная правка lock-файла и разовое удаление
    кэша не считаются устранением причины.

## Учёт проверяемых путей

### Источник и статус уточнения

REQ-0007.1 принят по прямому поручению владельца 2026-10-19 завершить
исправление требования после рассмотрения предложенной редакции.
Классификация — `specification_change` по
[порядку изменений DR-0010](../decisions/DR-0010.md#порядок-изменений).

Основание — задача проверки обязательного отсутствия файлов и каталогов,
а также поиска конфигурации по нескольким путям. Прежнее правило требовало
создать в успешном примере даже запрещённый путь и тем самым делало такой
контракт невыполнимым. Уточнение устраняет это противоречие и сохраняет защиту
от непроверенных входных данных в соответствии с
[назначением коллекции](../concept.md).

### REQ-0007.1. Учёт назначения проверяемого пути

Запускатель контрактных проверок должен различать следующие назначения пути:

- **Необязательные входные данные.** Операция читает данные при их наличии.
  Такой вход объявляется в `inputs` и присутствует хотя бы в одной фикстуре
  успешного сценария операции. Проверка внешнего результата подтверждает
  обработку входа. Для входа JSON сохраняется проверка содержательности данных.
- **Запрещённый путь.** Наличие файла или каталога по этому пути нарушает
  контракт проверяемой операции. Отсутствие проверяется успешным сценарием,
  а наличие — сценарием ожидаемого отказа с проверкой причины. Требование
  присутствия в успешном примере к такому пути не применяется.
- **Кандидат поиска конфигурации.** Операция проверяет несколько возможных
  расположений. Отсутствие отдельного кандидата допускается без требования
  создать его в успешном примере. Сценарий проверяет использование найденной
  конфигурации, а при нескольких доступных кандидатах — установленный
  контрактом операции порядок выбора. Результат поиска без доступных
  кандидатов также проверяется по контракту операции.

Ожидаемое отсутствие объявляется для конкретного пути и сценария с объяснением
причины. Запускатель проверяет его после подготовки фикстуры, перед основной
командой, и сопоставляет с наблюдаемой проверкой пути во время команды.
Объявление разрешает только соответствующее наблюдение этого сценария.
Оно не отменяет требования к объявленным входным данным и не распространяется
на другие пути или сценарии. Для необъявленных отсутствующих путей успешного
сценария сохраняется отказ, кроме создаваемых или заменяемых выходов и состояния.
Отрицательная проверка типа существующего объекта по-прежнему не считается
отсутствием пути. Поле `inputs` остаётся обязательным для каждой операции,
пустой массив означает отсутствие найденных необязательных входных данных.

### Критерии приёмки REQ-0007.1

1. Успешный сценарий с объявленным и наблюдаемым отсутствием файла или каталога
   проходит без требования создать его в другой успешной фикстуре.
2. Если объявленный отсутствующим путь существует после подготовки фикстуры,
   запускатель отклоняет сценарий и называет путь. Если команда не проверила
   объявленный путь, запускатель отклоняет неиспользуемое объявление.
3. Парные сценарии запрета пути подтверждают успешное завершение операции
   при отсутствии пути и ожидаемый отказ с причиной при его наличии.
4. Поиск конфигурации проходит при отсутствующих промежуточных кандидатах.
   Проверяются влияние выбранной конфигурации на внешний результат, порядок
   выбора при нескольких доступных кандидатах и результат при отсутствии всех.
5. Объявление отсутствия настоящего входа в одном сценарии не заменяет
   успешный сценарий его обработки. Вход, отсутствующий во всех успешных
   фикстурах операции, отклоняется. Для JSON отклоняются также примеры,
   в которых все коллекции пусты во всех таких фикстурах.
6. Один путь может отсутствовать в одном сценарии и обрабатываться как вход
   в другом. Разрешение отсутствия не переносится между сценариями.
7. Необъявленный отсутствующий путь успешного сценария вызывает отказ.
   Создаваемые выходы и состояние, а также отрицательные проверки типа
   существующих объектов не вызывают ложного требования объявить вход.

### Формат контракта и совместимость

Запускатель читает версии контракта 2 и 3. Контракты версии 2 без нового поля
сохраняют прежнее поведение и не требуют миграции. Ожидаемое отсутствие
описывается только в версии 3 полем `cases[].absent_inputs`: массивом объектов
с безопасным относительным `path` внутри фикстуры и непустым объяснением
`reason`. Поле необязательно, его отсутствие равнозначно пустому массиву.
Повторяющиеся пути и неправильные значения отклоняются с указанием поля.

Поле `absent_inputs` в операции отклоняется с указанием перенести объявления
в конкретные сценарии версии 3. В версии 2 это поле в сценарии также
отклоняется. Более ранний запускатель должен отказать на версии 3, а не принять
сценарий с пропущенной новой проверкой. Неизвестная версия отклоняется без
изменения контракта. Это сохраняет совместимость по [REQ-0038](REQ-0038.md).

Отсутствие означает отсутствие любого объекта по пути, включая символическую
ссылку. Наличие объекта после `prepare` отклоняет сценарий до основной команды.
Неиспользованное объявление отклоняется и в сценарии ожидаемого отказа.

каталогов как входных данных этим уточнением не вводится.

Требование распространяется на справки
`ai-skill-development` и `ai-setup-apm`, исходник
`.apm/skills/ai-setup-apm/scripts/eval-tools/run-skill-script-contract-tests.py`,

## REQ-0007.2. Покрытие функций исходного скрипта

### Источник, статус и цель

Уточнение принято по поручению владельца «Исправляй» от 2026-10-20 после
перепроверки дефекта на Python 3.13.13 и 3.14.7 и предложений по исправлению.
Классификация — `specification_change`: обязательный учёт функций прежде
описывался в производной справке, но не был закреплён в требованиях.
Цель — сохранить обнаружение непроверенных функций без ложных отказов из-за
служебного кода вычисления аннотаций.

Основания поведения Python: PEP 649 «Deferred Evaluation Of Annotations Using
Descriptors», разделы «Overview» и «Compiler-generated __annotate__ functions»,
PEP 749 «Implementing PEP 649», раздел «The future of from __future__ import annotations»,
и справочник Python 3.14, раздел «Annotations» главы «Compound statements».
Они учтены в [источнике корпуса «Аннотации Python»](../../knowledge/data/pyan/source.yml).
Источники описывают язык. Правило проверки покрытия установлено владельцем проекта.

### Требование

При объединении покрытия контрактных сценариев запускатель должен отклонять
функцию, определённую в исходном скрипте, если ни одна исполняемая строка её
тела, отличная от строк сигнатуры и объемлющего кода, не выполнена и для функции нет
обоснованной записи в `unexercised_functions`. Если таких отдельных строк нет,
проверка по строкам не устанавливает невыполнение функции. Общая строка
сигнатуры и тела не считается отдельной строкой тела.

Служебный код вычисления аннотаций, созданный компилятором, не должен
создавать обязательную функцию покрытия. Его выполнение не должно засчитываться
как выполнение одноимённой функции исходного скрипта. Имя `__annotate__`
само по себе не освобождает пользовательскую функцию от проверки.

Исключение `unexercised_functions` содержит путь скрипта, полное имя функции
и непустую причину. Оно допускается для защитного отказа или зависимости от
внешнего окружения. Неизвестная функция и запись о фактически покрытой функции
вызывают отказ. Остальные непокрытые строки остаются диагностикой для проверки
по риску и сами по себе не требуют полного покрытия скрипта.

### Критерии приёмки REQ-0007.2

1. Вызванная аннотированная функция с многострочной сигнатурой, возвращающая
   переданный аргумент, проходит на Python 3.13.13 и 3.14.7 без исключения
   для служебной функции. Проверяются варианты
   с `from __future__ import annotations` и без него.
2. Невызванная функция с отдельными строками тела вызывает отказ, включая
   пользовательскую `__annotate__` с аннотациями и без них. После выполнения
   её тела проверка проходит.
3. Чтение аннотаций другой функции не скрывает невыполнение пользовательской
   `__annotate__`. Вложенные функции, методы, декорированные и асинхронные
   функции сохраняют проверку строк тела и полных имён.
4. Обоснованное исключение для непокрытой функции принимается. Неизвестное
   или устаревшее исключение отклоняется. Непокрытая отдельная ветвь вызванной
   функции сама по себе не вызывает отказ.

### Реализация и проверки

Применяется к исходнику
`.apm/skills/ai-setup-apm/scripts/eval-tools/run-skill-script-contract-tests.py`,
рабочей копии `tools/run-skill-script-contract-tests.py`, регрессиям
`tools/test-run-skill-script-contract-tests.py` и описанию контроля покрытия
в справке `ai-setup-apm`. Формат контракта и допустимые версии не меняются.
Проверка по строкам не доказывает факт каждого вызова или полное покрытие ветвей.
