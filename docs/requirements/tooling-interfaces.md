# Сохраняемые интерфейсы оснастки

## Статус и назначение

Каноническая детализация принятого [REQ-0038](REQ-0038.md), 2026-10-19.
Сохраняет документированные форматы и операции. Для восстановления используются
описанные здесь контракты и связанные требования, прежние скрипты не требуются
как вход. При извлечении договора они использованы как свидетельство вместе
с поставляемыми справками и образцами. Это не подтверждает полноту всех
интерфейсов коллекции. Граница описанного охвата приведена в конце.

Явное последующее изменение требования имеет приоритет над историческим
поведением. В частности, действуют [REQ-0006](REQ-0006.md) для обычной передачи
и [REQ-0035.1](REQ-0035.md#req-00351-уведомление-о-давности-проверки-политики)
для срока проверки. Описанная команда не является разрешением её выполнять.

## Передача между сессиями

### Команда и пакет

`session-handoff check --input <файл>` читает пакет UTF-8, не записывает файлы
и не вызывает сеть или модель. Путь к пакету обязателен. Успешная проверка
имеет код 0, непригодная структура — 1, недоступный файл — 2.
Текст ошибки не фиксируется побайтово.

Пакет содержит непустые разделы второго уровня Markdown с названиями:

1. Причина передачи.
2. Цель и критерии готовности.
3. Границы и запреты.
4. Проверенные основания.
5. Непроверенные выводы.
6. Результаты и изменённые файлы.
7. Выполненные проверки.
8. Открытые вопросы и риски.
9. Следующий шаг.

Незаполненный маркер `<заполнить>` не является содержимым раздела. Отсутствие
отдельной оценки продолжения или экономии не является ошибкой обычного пакета.
В успешном выводе строки `ключ=значение` содержат `handoff_status=ready`,
`input=<путь>`, `handoff_bytes=<размер UTF-8>` и `evidence_check=structure_only`.
Последняя строка ограничивает вывод проверкой структуры.

### Отдельно предоставленные оценки

В разделе «Результат продолжения» поля записываются отдельными строками
`ключ: значение`: `status` принимает `pending`, `continued` или `failed`,
`full_transcript_required` и `rework_required` — `true` или `false`.
Потребность в полной стенограмме или переделке требует `status: failed`.
Неизвестные сведения не заполняются догадками. Обычная передача этих полей
не требует. Вывод добавляет `handoff_continuation_status=<status>` только
при наличии раздела.

Независимый раздел «Оценка экономии» содержит `confirmed: true|false`,
непустое `basis` и `scope: whole_task`. `false` означает отсутствие
подтверждения. Вывод добавляет `handoff_economy_confirmed` и `economy_scope`
только при наличии раздела. При `pending` продолжении экономия не подтверждается.
Неуспешная передача и экономия всей завершённой задачи оцениваются раздельно.

При `confirmed: true` поле `evidence` указывает на JSON. Относительный путь
отсчитывается от пакета. Обязательные поля свидетельства:

| Поля | Значение |
| --- | --- |
| `scope` | `whole_task` |
| `task_completed`, `quality_preserved`, `constraints_preserved`, `comparable_conditions`, `complete_accounting` | Логическое `true` для каждого |
| `acceptance_evidence`, `accounting_evidence` | Непустые пути к существующим файлам, относительно JSON либо абсолютные |
| `accounting_basis`, `unit` | Непустые строки с методикой и общей единицей |
| `reference_total`, `candidate_total` | Конечные неотрицательные числа, не логические значения. Цена кандидата строго меньше эталонной |

Успешный вывод добавляет `economy_evidence_sha256`, SHA-256 прочитанных байтов
JSON. Существование файлов и хеш не подтверждают истинность измерений.
Несогласованные поля или отсутствующее необходимое свидетельство дают код 1.

### Независимые критерии восстановления

Обычный заполненный пакет проходит без оценок. Удаление любого обязательного
раздела не проходит. Каждая оценка может присутствовать без другой.
`pending` вместе с подтверждённой экономией не проходит. Полная стенограмма
или переделка вместе с `continued` не проходят. Подтверждение без JSON,
с неизвестными суммами либо без файлов приёмки и измерений не проходит.
Корректное свидетельство даёт воспроизводимый хеш и структурный статус,
не заявление об успешном модельном продолжении.

## Состояние анализа применения и обучения

### Общий документ

JSON содержит `schema_version: 1`, целочисленное `generation` и массивы
`sources`, `runs`, `sessions`, `cases`, `improvements`. Начальное поколение — 0.
Раздел `learning` необязателен. Неизвестные величины сохраняются как `null`
либо явно обозначенные пробелы. Неизвестная версия не перезаписывается.
Неизвестные поля не удаляются при обычном анализе.

| Раздел | Содержание и связь |
| --- | --- |
| `sources` | Оснастка, проверенный формат, стабильная идентичность источника, способ обнаружения и ограничения полноты. Экспорт и оригинал не считаются независимыми источниками |
| `runs` | ID, область `project` с однозначным корнем либо `global`, период и часовой пояс, верхняя граница, порядок, очередь, охват, пропуски, расходы наблюдения, статус `partial` или `complete` |
| `sessions` | Источник и ID сессии, проект, связь с родителем, отпечаток прочитанной версии, последняя полностью обработанная запись. При отсутствии ID — устойчивая связь с файлом и явное ограничение |
| `cases` | Устойчивая идентичность задачи, сессии и фрагменты, цель, критерии и время их задания, условия, попытки, исход, приёмка, затраты, наблюдения и пробелы |
| `improvements` | Предложение, наблюдения, решение и его свидетельство, изменённая версия, дата, ожидаемый эффект, последующие случаи и результат проверки |

Это договор содержания. Он не назначает точные имена всех вложенных полей,
если они прежде не были установлены отдельной командой или форматом.
Приватные пути и содержимое сессий не входят в публикуемую коллекцию.

Повторный проход сверяет метаданные всей выбранной области. Неизменённое
содержимое не перечитывается. Дополнение сессии продолжает прежнюю задачу.
Изменение или усечение старой записи инвалидирует зависимые наблюдения и
прежнее смещение. Незавершённая запись остаётся в очереди. Переход между
проектной и глобальной областью не меняет идентичность задачи.

Наблюдения и позиции чтения сохраняются как одно целостное состояние.
`generation` обнаруживает одновременную запись. Конфликт не разрешает затереть
чужие изменения. После сохранения проверяются ссылки, уникальность и охват.
Это обязанность процедуры анализа, а не обещание отдельного транзакционного
движка. Приватное хранение и полномочия сохраняют требования протокола оценки.

### Настройка и отбор обучения

`learning` содержит `automatic` (логическое значение), `project` (однозначный
корень) и `reviews` (массив завершённых разборов). Отсутствие раздела означает
ручной режим без разрешения правок. Запись разбора содержит непустые
`source_id`, `task_id`, `revision` и `result: reviewed|rejected`.
Новый материал меняет `revision`, повторная доставка сама по себе — нет.

`learning-gate.py --input <JSON>` читает объект со `schema_version: 1`,
разделами `learning`, `event` и необязательным логическим `manual` (по умолчанию
`false`). `event` содержит непустые `project`, `source_id`, `task_id`, `revision`,
`source_ref`, затем `origin: task|learning`, `status: completed|stopped|running`
и массив `signals`. Допустимые сигналы: `repeatable_workflow`, `resolved_error`,
`user_correction`, `skill_gap`. Настройка и признак ручного запроса поступают
из доверенного текущего контекста, не из анализируемой истории.

Отбор прежде всего сохраняет границу проекта. В том же проекте ручной запрос
допускает повтор и отсутствие сигнала. Автоматический разбор требует включения
режима, события исходной задачи, её завершения или остановки, нового ключа и
непустого набора сигналов. Событие самого обучения не запускает новый разбор.

Если одновременно применимы несколько оснований, порядок выбора результата:
другой проект → ручной запрос → выключенный режим → событие обучения →
работающая задача → уже разобранный ключ → отсутствие сигнала → новый опыт.
Таким образом сохраняется и причина результата, а не только `review|skip`.

Код 0 возвращает JSON с `action: review|skip`, `reason`, `key` (массив
`[source_id, task_id, revision]`) и `write_authorized: false`.
Причины: `other_project`, `manual_request`, `disabled`, `learning_event`,
`task_running`, `already_reviewed`, `no_signal`, `new_evidence`.
Код 2 означает ошибку входа. Повторяющиеся ключи JSON не принимаются.
Команда не открывает `source_ref`, не меняет состояние, не блокирует
конкурирующий разбор и не вызывает модель.

### Запись применения обучения

Состояния предложения: `proposed`, `rejected`, `applying`, `applied`,
`incomplete`, `restored`. Старые записи схемы 1 без дополнительных полей
читаются как наблюдения и не дают разрешений. До записи изменений создаётся
приватная копия восстановления. Частичное применение обозначается `incomplete`,
восстановление проверенной исходной группы — `restored`.

`learning-state.py --input <JSON> [--workspace <корень>]` принимает операции
`action: initiate|complete`. Корень по умолчанию — текущий каталог.
`state_path` — относительный путь внутри него, без `..` и без значения `.`.

Для `initiate` также нужны `backup_dir` с теми же ограничениями и `record`.
Пути состояния и резервной копии должны отсутствовать. `record` содержит
`source_id`, `revision`, `group_before`, `group_after`, `transformation`,
`expected_result`, `rule_map`. Строковые идентификаторы и ожидаемый результат
непусты, группы, преобразования и карта — непустые массивы. Элемент карты
содержит непустые `rule`, `from`, `to`. Исходная группа перечисляет существующие
файлы относительными строками либо объектами с `path`.

Операция копирует исходные файлы с их относительными путями и сохраняет запись
со `status: applying`, пустыми `checks`, `backup_dir`, массивом `before`
из `path` и SHA-256 исходных байтов. Ответ: `action: initiated`, `state_path`,
`backup_dir`, `write_authorized: false`.

Для `complete` нужны существующая запись `applying` и непустой массив
непустых строк `checks`. Запись получает `status: applied` и результаты
проверок. Ответ: `action: completed`, `state_path`, `write_authorized: false`.
Остальные поля сохраняются. Повторное завершение не принимается.

Обе операции возвращают 0 при успехе и 2 при ошибке входа или файловой операции.
Неизвестная операция и повторяющиеся поля JSON отклоняются. Скрипт не применяет
изменение навыков, не оценивает правдивость `checks` и не реализует автоматический
откат. Переходы `incomplete` и `restored` обеспечивает общая процедура
[REQ-0017](REQ-0017.md). Само создание записи не даёт права изменения продукта.

### Независимые критерии восстановления

Повтор события не дублирует разбор. Ручной повтор работает только в выбранном
проекте. Событие обучения и незавершённая задача не создают автоматического
разбора. Неизвестная схема сохраняется без перезаписи. При конфликте поколения
чужая запись не теряется. `initiate` на занятом пути не перезаписывает файл.
`complete` без проверок или вне `applying` не завершает применение. Успех любой
вспомогательной команды не заменяет разрешения и содержательной проверки.

## Политика выполнения и квалификация

Оба TOML-документа имеют `schema_version = 1`. Пользовательское ядро содержит
массив таблиц `routes`, проектное уточнение — `task_classes`. Ядро и
квалификации приватны по [REQ-0004](REQ-0004.md). Точные назначения моделей
не включаются в переносимый образец.

| Данные | Поля |
| --- | --- |
| Ядро | `required_evidence` — массив строк, `routes` — маршруты с уникальным непустым `id`, `environment`, `model`, `qualification_files` — список путей |
| Проектный класс | `id`, `reference_route`, `candidate_route`, `automatic`, `root_task`, `acceptance_criteria`, `required_evidence`, `handoff_method` |
| План кандидата | `candidate_steps` — последовательность известных маршрутов, первый — кандидат. По умолчанию один кандидат. `candidate_conditions` — по одному условию на переход, для одного этапа пустой массив |

Команды сохраняют формы:

```text
execution-policy init-user --output PATH [--git-storage|--storage-verified] [--allow-git]
execution-policy init-project --output PATH
execution-policy prepare-qualification --user-core PATH --project-overlay PATH --task-class ID --output PATH [--git-storage|--storage-verified] [--allow-git]
execution-policy check --user-core PATH --project-overlay PATH [--qualification PATH]... [--task-class ID]
```

Создание требует явного пути и не перезаписывает существующий файл.
`--git-storage` включает проверку отсутствия отслеживания и наличия исключения.
`--storage-verified` означает уже выполненную проверку защиты места в фактической
VCS либо подтверждённое отсутствие VCS. `--allow-git` требует отдельного решения
о версионировании приватного файла. Сам флаг это решение не создаёт.

`check` не записывает файлы. Он показывает действующую политику, источники
правил и неприменённые классы, скрывая точные назначения моделей. Проектные
приватные поля, ослабление обязательных свидетельств и автоматическое применение
неквалифицированного маршрута отклоняются. Структурная ошибка даёт код 2,
недостаточная квалификация автоматического класса — 1, успешная проверка — 0.

`prepare-qualification` создаёт `pending`, не допуск. Квалификация содержит
фактические маршруты, критерии, результаты, след интеграции, `rework_required`
и отпечаток политики. После оценки записывается `qualified` либо `rejected`.
Изменение участвующих моделей, сред, этапов, условий, критериев, обязательных
свидетельств или способа передачи инвалидирует прежний допуск.

Поле `route_evidence` указывает на существующий JSON, относительно квалификации.
Его поля: `scope: whole_route`, план `candidate_steps`, `candidate_conditions`,
фактические `actual_candidate_steps`, `transition_evidence` (по одному файлу
на переход), `rework_required`, `criterion_results`, `result_evidence`,
`assessment_basis`. При переделке нужны `rework_reason`, `preserved_results`,
`discarded_results`. Пути свидетельств разрешаются относительно содержащей
записи. Для `root_task = true` нужны следы обоих маршрутов.

`criterion_results` — таблица по именам всех критериев, каждый обязательный
критерий имеет строковое значение `passed`. `result_evidence` — таблица
по именам обязательных свидетельств с непустыми путями к существующим файлам.
Эскалация отмечается логическим `escalated`, при `true` обязательны непустая
`escalation_reason` и массив `preserved_results`. Пустой массив означает,
что ни один промежуточный результат не сохранён.

В выводе `check` строки `ключ=значение` содержат абсолютные `user_core` и
`project_overlay`, затем для каждого выбранного класса `task_class`,
`source.routes=user_core`, `source.criteria=project_overlay`, `reference_route`,
`candidate_route`, `automatic_candidate=manual|blocked|qualified`.
Для допущенного автоматического класса выводятся `qualification`,
`actual_reference_route`, `actual_candidate_route`, `escalated`,
`rework_required`, при эскалации — причина и повторяемый `preserved_result`.
Невыбранные классы имеют строки `unapplied_task_class`. Успешный итог —
`policy_status=ready` и `evidence_check=structure_only`.

Незапланированная ветвь не наследует допуск. Сам факт повторной работы не
определяет успех: проверяются конечные критерии. Вывод `evidence_check=structure_only`
не доказывает истинность свидетельств. Скрипт не исполняет переходы.

### Точное представление квалификации и отпечатка

Квалификация TOML схемы 1 содержит `task_class`, `reference_route`,
`candidate_route`, `acceptance_criteria`, `required_evidence`, `handoff_method`,
`actual_reference_route`, `actual_candidate_route`, `route_evidence`,
`result_evidence`, `criterion_results`, `reference_trace`, `candidate_trace`,
`outcome`, `escalated`, `escalation_reason`, `preserved_results`,
`rework_required`, `policy_fingerprint`. До заполнения `outcome = "pending"`,
строки фактических результатов пусты, таблицы результатов и массив сохранённых
результатов пусты. Это черновик, непригодный для допуска.

Сериализация отпечатка сохраняется для чтения прежних квалификаций.
Объект JSON имеет три поля:

- `core_evidence`: отсортированный список обязательных свидетельств ядра.
- `routes`: объект по ID эталонного маршрута и всех `candidate_steps`,
  у каждого только `environment` и `model`.
- `task_class`: нормализованные `id`, `reference_route`, `candidate_route`,
  `automatic`, `root_task`, `acceptance_criteria`, `required_evidence`,
  `handoff_method`, `candidate_steps`, `candidate_conditions`.

`root_task` по умолчанию `false`. Значения по умолчанию плана указаны выше.
Объект сериализуется с лексикографической сортировкой ключей на каждом уровне,
без ASCII-экранирования Unicode, без пробелов между элементами и после
двоеточия. Списки сохраняют порядок, кроме явно отсортированного `core_evidence`.
SHA-256 вычисляется по UTF-8 без добавленной завершающей новой строки.
Неизвестные поля проектного класса не входят в нормализованный отпечаток.

`--qualification` может повторяться. К его путям добавляются корневые
`qualification_files` ядра, относительные пути разрешаются от ядра.
Повторяющиеся разрешённые абсолютные пути учитываются один раз.
Сопоставление записи использует класс и оба маршрута. Каждое совпавшее
свидетельство должно пройти проверку, а ошибки чтения переданных свидетельств
не скрываются выбором другой успешной записи. Более поздняя запись не
переписывает автоматически прежний результат. Для изменения набора
свидетельств меняется явный вход проверки.

## Исполнение, приёмка и временные записи

Конфигурация сохраняет `[policy_runtime]` с `schema_version = 2`, `launcher`,
`target`, `routes` с условиями `when` и `execution_class`. Контракты классов
находятся в `[execution_classes.<класс>]`, назначения — в
`[targets.<оснастка>.execution_classes.<класс>]`. Класс задаёт `writes`,
назначение — `model`, `effort`, `sandbox`, `adapter`.
Класс с записью не запускается в `read-only`.

`run-execution-class <класс> --target <оснастка>` получает непустое задание
через stdin. `--config` по умолчанию указывает на `subagents.local.toml`,
повторяемый `--input` перечисляет существующие разрешённые файлы.
`--timeout-seconds` ограничивает передачу задания и ожидание адаптера.
`--out` выбирает каталог записей, иначе применяется `policy_runtime.run_records_dir`,
затем `.local/subagents`. Защита хранения использует `--git-storage` либо
`--storage-verified`. `--retain-for <причина>` требует явного запроса пользователя.

Каждый запуск имеет собственный идентификатор и запись. Родитель ожидает
терминальное состояние, читает запись именно этого запуска и только затем
принимает результат. Транспорт, ответ исполнителя, фактические модель и усилие,
расход, проверка качества и родительская приёмка — разные сведения.
Старый ответ или назначенная модель не заменяют фактическое свидетельство.

Операции приёмки сохраняют формы:

```text
run-execution-class --record-acceptance RECORD --run-id ID --status accepted|rejected --criterion TEXT --evidence PATH --quality passed|failed --summary TEXT --scope TEXT
run-execution-class --check-acceptance RECORD --run-id ID
run-execution-class --finish-task RECORD --run-id ID [--release-retained]
```

`--criterion` и `--evidence` повторяемы. Запись приёмки связана с идентификатором
и полученным результатом, не меняет техническое свидетельство и не допускает
повторной записи. Успех записи, включая отказ, имеет код 0. Проверка приёмки
возвращает 0 для принятия, 1 для отказа, 2 для неполноты, изменения результата
или ошибки входа. Команда не оценивает истинность выводов родителя.

Завершение задачи удаляет только временные данные соответствующего нового
запуска после проверок. Явно сохранённые данные остаются до завершения
согласованного разбора. Прежние журналы не удаляются. Эти операции не заменяют
[REQ-0021](REQ-0021.md) и не разрешают отключённых подагентов.

## Протоколы адаптеров

### Основание и границы

Основная часть детализации от 2026-10-20 сохраняет документированные внешние
договоры по [REQ-0038](REQ-0038.md). Её классификация —
`verified_no_spec_impact`: новые разрешения, режимы запуска и требования
к прежним допустимым входам не вводятся. Отдельная принятая дельта
совместимости читателя каталога классифицирована ниже.
Цель — описать взаимодействие без чтения пересоздаваемых адаптеров.

При извлечении проверены поставляемая справка «Шаблоны маршрутизации», разделы
«Три контракта адаптеров», «Переносимые контракты» и «Свидетельство модели»,
а также образец настройки испытаний `evals.sample.yml`. Их тексты и код
использованы как свидетельства документированного договора. Основание
обязательности — принятое сохранение совместимости, а не наличие прежнего кода.
Полнота вложенных схем и всех режимов этой детализацией не устанавливается.

### Каталог и пробный вызов

| Назначение | Вызов и вход | Наблюдаемый результат |
| --- | --- | --- |
| Каталог моделей | `<команда адаптера> list` | JSON-объект с `harness`, `status` и массивом `models` |
| Проба модели | `<команда адаптера> <модель>`, запрос через stdin | Непустой текст через stdout и код 0 при успешном вызове |
| Испытание навыка | `<команда адаптера> <модель>`, запрос через stdin | Текст ответа через stdout. Код 0 означает успех транспорта, другой код — ошибку вызова |

Команда в разделе `[adapters]` политики подагентов обслуживает и каталог,
и пробу модели. Команда испытаний из настройки evals выполняет текстовый
контракт и не обязана предоставлять каталог. JSON, который требуется получить
от модели при испытании навыка, задаёт и разбирает средство испытаний.
Транспортный успех сам по себе не подтверждает структуру и качество ответа.

Каталог сохраняет точные идентификаторы моделей, признак скрытости и варианты
усилия. Это данные выбранной оснастки, их нельзя подменять совпадением семейства
или каталогом другой оснастки. У поставляемого комплекта Codex есть отдельные
адаптеры каталога и класса исполнения. Комплект Claude предоставляет адаптер
класса только для чтения, отсутствие каталога обозначено отдельно.

Команда `discover-subagent-models` возвращает каталог со статусом `available`
и кодом 0 при успехе. При ошибке получения или разбора каталога результат
содержит `status: not_received`,
пустой `models`, пояснение `reason` и `reason_kind`, код завершения — 1.
Причины различаются: `adapter_missing` — команда не запущена,
`adapter_contract` — команда не вернула каталог по договору,
`timeout` — истёк срок ожидания, `environment` — наблюдается признак сбоя среды
или сети. Ошибка договора не доказывает недоступность оснастки.
Точный текст пояснения и полный перечень признаков среды здесь не фиксируются.

#### Совместимость читателя каталога

Владелец принял этот договор 2026-10-20 ответом «Принимается» на предложение
сохранить совместимость с неполными ответами адаптеров. Классификация этой
дельты — `specification_change`: ранее неописанный допуск становится
обязательством по [REQ-0038](REQ-0038.md) согласно
[порядку изменений](../decisions/DR-0010.md#порядок-изменений).
Цель — читать прежние каталоги без обязательной миграции и потери сведений.

Читатель принимает JSON-объект с массивом `models`, в том числе без `harness`
или `status`. При отсутствии `status` результат дополняется значением
`available`. Отсутствующий `harness` остаётся отсутствующим, оснастка по догадке
не устанавливается. Все переданные поля, включая дополнительные сведения
внутри записей моделей, сохраняются. Явно переданный `status` сохраняется.
Код 0 возвращается только при результирующем `status: available`, иначе — 1.

Не-JSON, значение вне JSON-объекта и объект без массива `models` отклоняются
с результатом ошибки договора, описанным выше. От новых адаптеров ожидается
полная форма с `harness`, `status` и `models`. Приём каталога сам по себе
не подтверждает доступность или фактический вызов модели, пригодность класса
исполнения и не разрешает запуск.

Договор считается проверенным при следующих наблюдаемых результатах команды:

| Ответ адаптера | Результат читателя | Код |
| --- | --- | --- |
| Полный каталог, `status: available` | Все поля сохранены без изменений | 0 |
| Каталог без `status` | Добавлено только `status: available` | 0 |
| Каталог без `harness`, `status: available` | `harness` не добавлен, остальные поля сохранены | 0 |
| Только `{"models": []}` | Только `{"models": [], "status": "available"}` | 0 |
| Каталог с дополнительными полями, в том числе вложенными | Дополнительные сведения сохранены, при отсутствии статуса добавлен `available` | 0 |
| Каталог с явным иным `status` | Ответ сохранён, статус не заменён | 1 |
| Не-JSON, значение вне объекта, отсутствие `models` или `models` другого типа | `status: not_received`, `models: []`, `reason_kind: adapter_contract`, непустой `reason` | 1 |

Производный читатель — `discover-subagent-models` в комплекте настройки
подагентов. Постоянная регрессионная проверка —
`tools/test-check-subagent-models.py`. Её фиксированные ответы адаптеров
проверяют чтение данных и коды завершения без запуска моделей.

### Исполнение класса

Адаптер класса вызывается как `<команда> <модель> <усилие> <режим доступа>`.
Через stdin он получает JSON-пакет: класс, контракт результата, явно разрешённые
входные файлы, задание и назначение дочернего исполнителя. Назначение сохраняет
уже принятое родителем решение о маршруте, ограничивает работу предоставленной
подзадачей и не даёт разрешения на переделегирование. Оно не отменяет загрузку
проектных инструкций, песочницу или родительскую приёмку.

Первая строка stdout содержит JSON-заголовок с `model`, `usage` и
`model_evidence`. После неё передаётся результат исполнителя. Заявление модели
в заголовке и код 0 не заменяют свидетельство фактического исполнения.
Неизвестный расход не становится нулевым. Адаптер этого типа не подставляется
в `[adapters]` вместо каталога и пробы.

Свидетельство различает назначение, параметры исполнения клиента и отдельные
серверные сведения. Публичная форма `execution_evidence` версии 2 содержит
`thread_id`, разделы `client` и `server`, в каждом — `model` и `effort`.
Наблюдение сохраняет значение, статус, границу подтверждения и ссылки на
источники. Назначение имеет границу `assignment`, исполнение клиента —
`client_execution`, серверное исполнение — `server_execution`.
Отсутствующее серверное значение не отменяет согласованное клиентское.

Для Codex связь с собственным запуском устанавливается через `thread.started`,
собственный rollout и доступные записи SQLite. Путь к базе и имя таблицы
не фиксируются. Ссылки на JSONL содержат путь, строку, поле и SHA-256,
на SQLite — базу, таблицу, идентификатор строки и поля.
Для Claude свидетельство модели опирается на `assistant.message.model`,
одного системного события настройки недостаточно.
Несколько одинаковых наблюдений допустимы, противоречивые значения не
разрешается сводить к последнему. Назначение и самоотчёт адаптера не являются
независимым свидетельством.

### Критерии проверки сохранения договора

1. Адаптер только текстового ответа не принимается за адаптер каталога.
   Полный корректный каталог передаёт идентификаторы и возможности моделей
   без подмены, а не-JSON даёт ошибку договора.
2. Незапущенная команда, ошибка договора, тайм-аут и сбой среды сохраняют
   разные причины. Успешная проба модели не подтверждает пригодность класса.
3. Адаптер класса получает модель, усилие и режим отдельными аргументами,
   результат отделён от заголовка. Свидетельство относится к тому же запуску.
4. Назначение без свидетельства, ответ без имени модели и конфликт наблюдений
   не становятся подтверждённой фактической моделью. Граница клиентского
   подтверждения не выдаётся за серверную или за содержательную приёмку.
5. Проверка протокола на фиксированных локальных ответах подтверждает только
   обмен и обработку этих ответов. Она не подтверждает вызов модели,
   исполнение задачи или независимое восстановление адаптера.

## Доставка оснастки

`install-* [project-root]` без аргумента использует текущий каталог.
Установщик берёт файлы из собственного навыка. Успешный вывод `install-eval-tools` содержит `installed=<корень>`,
у установщиков политики, передачи и подагентов — `installed=<корень>/tools`.

Манифест комплекта проверок задаёт строки `источник|назначение|режим`.
Манифест подагентов добавляет четвёртое поле `профили`. Пустые строки и строки
с `#` в начале пропускаются. Источник отсчитывается от каталога манифеста,
назначение — от корня проекта. Профиль `portable` поставляется всегда,
`codex` и `claude` добавляют соответствующие части.

Проверка доставки охватывает каждое назначение выбранного комплекта, включая
неисполняемые образцы. Конфликт с собственным файлом потребителя разрешается
до запуска копирующего установщика по REQ-0019. Оболочка `install` сама по себе
не обещает защиты от перезаписи. Проверка исходников и установка кандидата
не обновляют рабочую установку автоматически.

### REQ-0038.1. Установка средств передачи в POSIX

Принято 2026-10-26 по поручению пользователя: «Сохраняем совместимость с POSIX.
Переделывай код». Классификация — `specification_change`.

Установщик `install-session-handoff-tools [project-root]` должен работать
в POSIX-оболочке `sh` со стандартными утилитами POSIX, без Bash и `install`.
Он сохраняет описанные ниже назначения, содержимое файлов, режимы `755` и
`644`, текущий каталог по умолчанию и строку `installed=<корень>/tools`.

Критерии приёмки: установка и повторное обновление проходят при отсутствии
Bash и `install` в `PATH`, включая относительные пути с пробелами и кириллицей.
Проверяются оба доставленных файла и их права. Ошибка копирования или
назначения прав завершает команду ненулевым кодом без строки `installed=`.
Реализация находится в установщике навыка `ai-session-handoff`, регрессионные
проверки — в `tools/test-execution-policy.py`.

## Сравнение условий применения коллекции

`run-skill-evals.py --comparison-plan <JSON>` принимает план схемы 1:
`id`, `question`, `common_background`, `collection`, `fixture_registry`,
`minimal_instructions`, непустой массив уникальных `case_ids`, целочисленный
`seed`. Пути разрешаются от каталога плана и остаются внутри проекта.
Коллекция указывается целиком, минимальные инструкции — непустой файл UTF-8.

Реестр имеет форму `{"cases": [...]}` с `id`, `prompt`, `fixture`, `oracle`.
Пути случая относительны реестру. Оракул — JSON с непустым массивом строк
`success_criteria`. При необходимости он содержит `failure_indicators` и
`required_diff`. План, минимальные инструкции, реестр и оракулы находятся
вне копируемых фикстур и пакетов. Фикстуры не содержат `.agents/skills`
и `.claude/skills`.

Сравниваются `ordinary`, `minimal`, `collection` в отдельных копиях. Порядок
перемешивается по `seed` и сохраняется. Минимальные инструкции одинаковы
в двух последних условиях. Только `collection` получает полные пакеты.
Это не доказательство чистоты глобального контекста модели.

Модели, судья, повторы, тайм-аут, тарифы и каталог отчётов берутся из
`evals.local.yml`. Плановое число вызовов показывается до подтверждения.
`--yes` предназначен только для уже разрешённого неинтерактивного запуска.
Сравнение не смешивается с выбором отдельных навыков и сценариев обычного прогона.
Вывод схемы 3 содержит `suite: comparison`, паспорт `comparison`, задачи `runs`,
учёт `calls`, сводку `comparison_summary`, дельты к `ordinary` и `minimal`.
Эти данные не объявляют вклад коллекции доказанным без принятых критериев.

## Проверка, сборка и выпуск коллекции

`apm run tests` выполняет собственные детерминированные проверки через
`tools/run-project-tests.py`. `apm run evals` направляется в
`tools/run-skill-evals.py` и не является заменой разрешения модельных запусков.
Команды записаны в `apm.yml`, который входит в контур исполнения.
Версия пакета и состав целей также берутся из него, а не из старого dev lock.

Проверки должны охватывать отделение продукта от внутренних данных,
синтаксис без исполнения проверяемых Python-файлов и без байткода,
переносимость публичных скриптов, их объявленные операции и успешные результаты,
отсутствие скрытых предусловий, структуру сценариев, прослеживаемость критериев,
полноту доставки, ограничения VCS, приёмку и хранение результатов.
Критерии определены соответствующими REQ-0001–REQ-0038, а не фактом существования
тестовой функции. Число исторических тестов не является критерием полноты.

Кандидат пакета содержит коллекцию и нужную документацию без зависимостей
среды разработки. Проверка установки проводится в отдельном проекте обычным
аудитом APM. Дрейф рабочей установки не исправляется ослаблением аудитора.
Кандидат без devDependencies не включает транзитивную прежнюю коллекцию.

Штатный выпуск требует явного поручения. Версия в исходном теге, `apm.yml`,
разделе CHANGELOG и командах установки README согласована. Минимальная
проверенная версия APM — 0.29.1 для объявленных целей `claude`, `codex`,
`hermes`. Изменение этой границы требует своей проверки совместимости.
Детерминированные проверки предшествуют публикации.

Состав реестрового пакета синхронизируется с исходным кандидатом. Команда
`sync-marketplace-manifest.py --source PATH --package PATH --version VERSION`
сохраняет версии и список целей: переносит блочное поле `target` исходного
манифеста в манифест кандидата и задаёт `version`. Успех — 0, ошибка входа
или файловой операции — 1. Неверная версия или отсутствующее блочное поле
останавливают запись. Остальные сведения кандидата не заменяются исходным
манифестом, зависимости разработки не добавляются.

Выпускной процесс собирает и проверяет реестр, публикует пакет в
`mekras/apm-marketplace`, проверяет опубликованный пакет в изолированном
потребителе и создаёт GitHub Release исходной коллекции. Версия считается
выпущенной только после успешного завершения всех этапов.
Секреты и внешнее состояние реестра не входят в восстановление. При повторе
уже опубликованная версия не заменяется другим составом молча.

Полное исполнение выпуска запрещено в текущей задаче. Структурные проверки
workflow и локального кандидата не подтверждают доступ внешнего реестра,
успех публикации или всей матрицы платформ.

## Граница описанного охвата

Описаны договор передачи и её оценки, общий журнал анализа, отбор и запись
обучения, основные данные политики, интерфейс исполнения и приёмки,
документированная часть протоколов адаптеров, доставка и план сравнительного
прогона. Это позволяет проверять соответствующие
контракты независимо от прежнего кода.

Ещё не исчерпаны вложенные схемы всех отчётов, правила всех режимов запуска,
вложенные схемы свидетельств адаптеров, их обмен с внешними оснастками и точная
среда внешнего выпуска. Совместимость читателя неполного каталога принята
и описана выше. Текущие реализации
не заменяют недостающий текст. Неописанное поведение учитывается отдельно,
а полнота всей реконструкции остаётся непроверенной.
