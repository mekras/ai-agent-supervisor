# Коллекция навыков для управления применением ИИ

Коллекция переносимых навыков для организации работы с ИИ в проектах разработки
ПО. Она помогает снизить риск неподходящего применения ИИ и сделать работу с ним
более проверяемой.

Коллекция предназначена прежде всего для проектов с `Codex` и `Claude Code`.
Она подключается через `APM`. Доступность конкретного навыка зависит от
возможностей агента и его среды.

Коллекция помогает:

- заранее отделять задачи, которые можно поручать ИИ, от задач с недостаточным
  контекстом или слишком высоким риском.
- собирать проверяемые основания и контролировать изменения правил, ролей,
  навыков, шаблонов и документации.
- настраивать `AGENTS.md`, APM, хуки и маршрутизацию подагентов.
- проверять результаты ИИ перед публикацией и дальнейшим использованием.
- разбирать нарушения правил как возможный дефект правил, маршрутизации или
  контрольной процедуры.

Коллекция опирается на практики разработки агентных систем, создания и оценки
навыков, настройки инструкций и безопасного применения ИИ. При её разработке
использовались материалы следующих источников:

- [Microsoft Learn: evaluation flow for Prompt flow](https://learn.microsoft.com/en-us/azure/machine-learning/prompt-flow/how-to-develop-an-evaluation-flow)
- [документации OpenAI Codex](https://developers.openai.com/codex)

## Установка

Установите [APM](https://microsoft.github.io/apm/), подключите реестр коллекции
и выполните в корне проекта команду для используемого агента:

```bash
apm marketplace add mekras/apm-marketplace --ref master
```

Для Codex:

```bash
apm install ai-agent-supervisor@mekras --target codex
```

Для Claude Code:

```bash
apm install ai-agent-supervisor@mekras --target claude
```

После установки навыки коллекции станут доступны агенту в этом проекте.

После этого настройте проект для работы с агентами. Попросите агента:

> Настрой этот проект для работы с агентами.

Чтобы обновить установленную коллекцию, выполните:

```bash
apm update
```

### Необязательные зависимости

Некоторые навыки предлагают необязательные сценарии автоматизации. Они
выполняют повторяемые проверки, экономят токены и делают результат стабильнее.
Если для такого сценария нет нужного интерпретатора или среды, навык продолжит
основной путь и сообщит, какую проверку не выполнил.

Для использования автоматизации рекомендуются Python 3 и совместимая с POSIX
оболочка. Каждый навык отдельно указывает необходимые средства и ограничения.

### Проверки

Проверки разделены на две команды.

Обязательная проверка не вызывает модель или сеть. Для проверки исходного
репозитория нужны Python 3, Git, APM и пакет PyYAML:

```bash
apm run tests
```

Она проверяет бюджеты описаний навыков, сценарии срабатывания и результата,
скрытые символы Unicode, Python-байткод в исходниках, проекциях и lock-файле,
безопасную синтаксическую проверку, границу публичного продукта, установку в изолированный
тестовый проект, успешные рабочие сценарии поставляемых Python-скриптов и
согласованность оснастки модельных прогонов.

Модельный прогон — отдельная необязательная команда для измерения качества:

```bash
apm run evals
```

Он проверяет маршрутизацию по `evals/triggers.json` и запускает проектные
фикстуры из `evals/fixtures/`. Каждый повтор получает отдельную копию проекта:
`baseline` — без проверяемой коллекции, `skill` — с предложенным целевым
навыком, `catalog` — с предварительным выбором из каталога. В двух последних
режимах доступны полные пакеты навыков со справками, шаблонами и скриптами.
Агент может выбрать несколько навыков или ни одного и изменить выбор по ходу
задачи. Доступность полного комплекта не означает загрузку всех его материалов.

Отчёт схемы 3 разделяет ответ модели, маршрутизацию и свидетельства выполнения:
начальный и конечный снимки файлов, diff и журнал адаптера. Отсутствующий журнал
не заменяется рассказом агента о выполненных командах. Оракул фикстуры не
передаётся кандидату. Сценарии `result-scenarios.json` также выполняются в
рабочей копии, но их критерии могут быть видны в полном пакете навыка. Такие
сценарии проверяют регрессию процедуры, а не служат слепым сравнением.

Неуспех `baseline` — ожидаемое наблюдение, а не ошибка запуска. Успешный
прогон требует прохождения режимов `skill` и `catalog` и отсутствия ухудшения
их доли прохождения относительно baseline. Маршрутизация оценивается отдельно
от успеха задачи. Эти технические режимы сами по себе не реализуют три условия
внутреннего сравнительного протокола и не доказывают пользу коллекции.

Для отдельного сравнения обычного агента, минимальных инструкций и полной
коллекции подготовьте [план сравнения](.apm/skills/ai-setup-apm/references/comparison-evals.md)
и запустите `python3 tools/run-skill-evals.py --comparison-plan evals/comparison/plan.json`.
Запускатель фиксирует входы до вызовов, сохраняет результаты по каждой модели
и условию. Проигрыш коллекции допустим как наблюдение. Отчёт описательный,
полезность коллекции автоматически не подтверждается.

#### Настройка модельного прогона

Средство запуска вызывает модель через адаптер по переносимому контракту:
`<команда адаптера> <модель>`, запрос на стандартном вводе, текст ответа на
стандартном выводе. В проекте есть адаптеры для Codex CLI и Claude Code в
`tools/adapters/`. Для другой среды добавьте адаптер по тому же контракту.

Для выполнения фикстур и сценариев результата перечислите модели в
`workspace_models`. Их адаптеры должны работать в `APM_EVAL_WORKSPACE` и
сохранять изменения в ней. Поддерживающий журнал адаптер пишет события
исполнения в `APM_EVAL_TRACE`, отдельно от ответа. Поставленные адаптеры Codex и
Claude используют этот канал. Копия проекта не является песочницей ОС:
ограничения доступа и общие пользовательские настройки определяет оснастка.
Перед модельным прогоном проверьте их и используйте только безопасные тестовые
данные. Для рабочей копии нужен Git, для адаптера Claude с журналом — Python 3.

Чтобы сохранить фактическую телеметрию, адаптер может вместо простого текста
вернуть JSON-объект `{"output":"<ответ модели>","usage":{...}}`, где `usage`
содержит `input_tokens`, `output_tokens`, при наличии `cost`, `currency` и
`elapsed_seconds`. Метаданные сообщает адаптер, а не проверяемая модель.
Сведения сохраняются и при ошибке вызова, если адаптер вернул полную обёртку.
Старый текстовый формат поддерживается.

Отчёт сохраняет каждый вызов в `calls`, включая выбор навыков, повторы и
ошибки кандидата или судьи. Сценарии связываются с ним через `call_ids`.
В `accounting` фактические и оценочные суммы разделены по валютам.
Неизвестная стоимость обозначается `null`. Итог `total_cost` доступен только
при фактической сумме каждого вызова в одной известной валюте.
Для оценки по `pricing` нужны обе ставки и валюта. Оценка токенов по длине
видимого текста не учитывает скрытый контекст и внутренние вызовы оснастки.
Журналы событий автоматически не превращаются в сведения о биллинге.
Даже полный учёт вызовов адаптера не означает измерения полной цены задачи.

Адаптеры, список моделей и модель-судью задаёт локальный файл настроек
`evals.local.yml`. Он не попадает в Git: средство запуска создаёт его из
`evals.sample.yml` при первом запуске `apm run evals` и добавляет в
`.git/info/exclude`. YAML сохраняет комментарии и удобен для ручного
редактирования. Запускатель разбирает документированное подмножество формата
средствами стандартной библиотеки, поэтому PyYAML не требуется. В разделе
`adapters` задайте соответствие имени адаптера и команды, а модели и судью
указывайте в формате `адаптер:модель`. Ключи и подписку передавайте через
переменные окружения адаптера, а не через этот файл.

```yaml
adapters:
  adapter: path/to/adapter
models:
  - adapter:model
workspace_models:
  - adapter:model
judge: adapter:judge-model
timeout: 900
repetitions: 3
results_dir: eval-results
```

Формат `адаптер:модель` позволяет в одном прогоне сочетать модели от разных
адаптеров. Каждая запись проверяется по одинаковым критериям, поэтому результаты
сопоставимы.

#### Выборочный запуск

Для быстрой проверки одного навыка:

```bash
APM_EVAL_PATH=.apm/skills/ai-skill-development apm run evals
```

Для повторного запуска одного модельного сценария:

```bash
APM_EVAL_PATH=.apm/skills/ai-skill-development APM_EVAL_CASE_ID=ai-skill-development-result-stale-existing-tests apm run evals
```

Для ограниченной локальной проверки можно временно сократить число сценариев
результата:

```bash
APM_EVAL_LIMIT=1 apm run evals
```

Перед каждым живым прогоном запускатель показывает число вызовов кандидата и
судьи и спрашивает подтверждение. В неинтерактивной среде после просмотра
оценки добавьте `--yes` напрямую к запускателю. Модельный прогон после каждой
правки не обязателен. Выбирайте его для конкретного риска или воспроизведения
наблюдаемого сбоя и сохраняйте отчёт выбранных сценариев. При изменении общей
маршрутизации или оснастки расширяйте охват с учётом затронутых свойств.
Обязательная проверка проекта остаётся отдельной командой `apm run tests`.
Выводы о полезности коллекции основывайте на реальном применении.

## Выпуск

Перед выпуском обновите `version` в `apm.yml` и перенесите изменения из раздела
«Невыпущено» в раздел этой версии в `CHANGELOG.md`. Номер тега исходного
репозитория должен в точности совпадать с `version`, например `2.3.22`.

После отправки такого тега GitHub Actions проверяет коллекцию, переносит её
публичный состав в `mekras/apm-marketplace`, пересобирает описания реестра и
создаёт тег пакета `ai-agent-supervisor--v<версия>`.

Для первого автоматического выпуска добавьте в настройках репозитория
`mekras/ai-agent-supervisor` секрет Actions `APM_MARKETPLACE_TOKEN`. Это должен
быть тонко настроенный personal access token с правом **Contents: Read and
write** только для репозитория `mekras/apm-marketplace`.
